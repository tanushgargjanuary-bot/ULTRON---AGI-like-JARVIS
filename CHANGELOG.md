### A fresh install is checked, and Dependabot keeps to the pins, 2026-11-25

**Asked for.** "Please merge the pull request" (#37). My question had said that merging it also meant starting this piece, the next step of "make this repository ready to use". Nothing new to use: no setting, no dependency, no change to the app, no referee file.

**What was wrong.**
- CI never installed `requirements.txt`. `verify.yml` installs a short list written into the workflow, so a change to that file, or a dependency that shipped a bad release inside its allowed range, was installed by nothing, and a green run said nothing about whether a fresh clone installs. Dependabot's #34 showed it: on Python 3.11, which the readme supports, its file could not be installed (`numpy>=2.5.5` needs Python 3.12), and every check was green.
- 29 tests of the phone dashboard were skipped in CI, because the short list has no `fastapi`.
- Dependabot's default for an app raises every minimum to the newest release, which is how #34 came to ask for that numpy. It also moved the PyQt6 ceiling that `requirements.txt` keeps below Qt 6.12 on purpose.
- `scripts/bootstrap.py` ignores which optional packages failed to install (by design: one optional package must never stop the app) and exits 0, so on its own it cannot say that a line of the file did not install.

**What changed.**
- `.github/workflows/install-check.yml` (new, not a required check). `install` runs the launcher's own setup as `run.bat` does, on a clean Windows machine, for each Python the launcher accepts (3.11, 3.12 and 3.13, read from its `MIN_PY` and `MAX_PY`), then `scripts/check_install.py`. `suite` runs the whole suite on Linux with every package installed. It runs when a requirements or launcher file changes, on the 15th of each month, and by hand.
- `scripts/check_install.py` (new): asks pip what it would still install (`--dry-run --report`), then runs `pip check`. It installs nothing; exit 1 names what is missing or inconsistent.
- `.github/dependabot.yml`: the pip entry uses `versioning-strategy: widen` and ignores PyQt6 minor and major releases, with the reason written beside the rule. The grouped, one-at-a-time form is unchanged.
- `DECISIONS.md` row 136, `docs/TEST_AUTOMATION.md` (lane 3) and the handoff say so.

**Evidence.** `tests/test_check_install.py` (13 tests, red until the script existed) and 14 new tests in `tests/test_dependency_policy.py` (red on the old tree: no workflow, no strategy). 27 planted mistakes, all caught: a matrix that loses 3.13 or gains a version the launcher refuses, the strict step removed or run first, a lost trigger path, the schedule or manual runs removed, no time limit, no permissions, an unpinned action, a job named like a required check, `increase` instead of `widen`, the Qt rule or ceiling changed, and seven faults in the script. The script, run for real in a brand-new environment built by the launcher: "Every line of requirements.txt that applies here is installed", exit 0. With one package removed it names the package and exits 1. On #34's file with Python 3.11 it prints pip's own "No matching distribution found for numpy<3,>=2.5.5" and exits 1. The documentation of `versioning-strategy` (supported for pip) and `ignore` was read on 2026-11-25.

**Not verified.** The workflow on GitHub: it runs for the first time on the pull request that adds it (a change to the workflow file triggers it). ### Mute means muted, 2026-11-24 — the fourth piece of Mark LVII, written test first

**Asked for.** "Do the next piece": the mute half of the volume and mute piece, proposed at the end of the last one with a guess of "yes". Nothing new to use: no setting, no dependency, no network call, no referee file.

**What was wrong** (`actions/computer_settings.py`; read in the code, and shown by the new tests failing on it):
- "Mute", "unmute" and "toggle mute" were one function. On Windows and Linux it was a flip (the mute key, or `pactl set-sink-mute … toggle`), so "unmute" on a machine that was not muted muted it, and "mute" said twice unmuted it again. On macOS it always muted, so "unmute" muted.
- The answer read the volume level before and after. Muting does not move the level, so it was always "unverified", with a reason about the volume.
- "Undo" after a mute put the volume level back, which changes nothing that can be heard.
- The model was shown the word `mute` and never `unmute`.

**What changed.** The three words are three actions that set the state asked for: `mute_get` reads the state, `mute_set` sets it, and a toggle reads first and then sets the opposite. The answer is read back from the mute flag, undo puts the flag back, and the model is now told `unmute`. That last part has to ride along: with `mute` meaning only "mute", a model that was never told `unmute` would mute when the user said "unmute". Windows uses the audio interface that the volume code already used; the mute key stays as the last resort when that cannot be reached, and then the answer says that nothing could be confirmed.

**Different from Mark's version** (`752ff61`, read, not copied): `pactl` is asked in plain English (`LC_ALL=C`), because it prints the yes or no in the user's language (`pa_yes_no_localised` in PulseAudio's `pactl.c`, read) and a translated answer would have made every reading "unknown"; a toggle whose starting point could not be read is reported as not confirmed, where his code reports it as confirmed; `toggle_mute` is not added to the words the model is shown (see the next paragraph).

**Found while reading, not changed.** `core/policy.py` lists this tool's actions as `volume`, `set_volume` and `brightness`, but the actions are `volume_up`, `volume_down`, `volume_set`, `brightness_up`, `brightness_down` and `toggle_mute`. `policy.classify("computer_settings", {"action": "volume_up"})` answers guarded and not allowed, and `core/custom_gate.dispatch` answers a guarded call with a confirmation banner on the HUD. So "volume up" should ask for a click, while "mute" and "unmute", which the table names correctly, do not. Read in the code and run through the policy function; **not seen in the running app**. It is a referee file, so it was not edited, and whether these names should be routine is the owner's decision. It is also why `toggle_mute` is not shown to the model: it would add one more banner.

**Not taken yet** (the next piece): `volume_set` switching the sound on when it sets a level, the volume-key fallback, the volume step size, brightness on macOS and Linux, and the rest of that file's changes.

**Evidence.** `tests/test_mute_state.py`: 18 tests. 13 fail on the original code; the other 5 guard what must not change (the volume level is never touched, and every word the model is shown still resolves). All 18 pass on the new code. A stand-in machine holds one mute flag and is reached the three ways a real one is: Windows (the audio interface and the mute key), macOS (`osascript`) and Linux (`pactl`). 29 faults planted one at a time in the new code (a flip instead of a set, true and false swapped on each system, a reading read upside down, an undo that restores the opposite, an answer that never compares, the wrong audio device, and so on): all 29 are refused. ### One test failed by chance on Windows, 2026-11-22 — a rest time read back through floating point

**What happened.** The run on `1abb11f` (run 45037801726), a commit that changed only documents, passed on Linux and failed on Windows in one test: `test_gemini_resilience.LadderBehaviour.test_an_exhausted_model_is_rested_for_the_quota_time`, `AssertionError: 300.00000000000006 not less than or equal to 300`. The test came in with pull request #22 and had passed on Windows in earlier runs. It has nothing to do with the follow-up system.

**Why.** The test works out how long a model is rested as `deadline - now`, where the deadline was `monotonic() + 300` read a moment earlier (`monotonic()` is the clock the program uses to measure spans of time). Python 3.12 on Windows moves that clock in steps of 15.6 milliseconds, so two reads in a row often give the same number; on Linux the steps are nanoseconds. With the same number twice the answer should be exactly 300, but a computer keeps about 15 digits, and `(t + 300) - t` is not always exactly 300: for `t` = 212.007 seconds (a runner that had been up a little over three and a half minutes) it is 300.00000000000006. By arithmetic over every millisecond of uptime, 23% of the ticks between 212 and 512 seconds fail that check, and the sibling test for the 30-minute rest (`test_an_overloaded_model_is_rested_for_the_short_time`) fails at 13 to 25% of the ticks between 212 and 2,048 seconds. How often a hosted run fails is **not measured**: it depends on how long the runner had been up when the test ran. That the clock did not move between the two reads is inferred from the result (a later read would have given less than 300), not seen.

**What changed (a test file only, `tests/test_gemini_resilience.py`).** Inside the four tests of that class, `core/gemini.py` sees a clock that stands at 1,000.0 (a small stand-in for the `time` module; everything else on it stays real), so the sum is exact and the tests say what they mean: this model is rested for exactly this long. **Two assertions were replaced** (flagged, as the project's rules ask): `assertLessEqual(remaining, N)` is now `assertEqual(remaining, N)` in the quota test and the overload test. A result that is equal is also less-or-equal, so neither assertion is weaker.

**Evidence.** The old tests with the process clock stopped at 212.007 seconds fail with the exact message of the hosted run; at 248.001 seconds the overload test fails with `1800.0000000000002 not less than or equal to 1800`; at 1,748.019 seconds both fail. The new tests pass at those seconds and on the real clock (by construction: they no longer read the process clock). Six wrong rest times planted in `core/gemini.py`: the new tests catch all six, the old tests three (they accept a quota rest of 299 seconds or of 1 second, and an overload rest of 1,799 seconds). Ruff finds nothing new. **Not verified:** the fix on Windows itself. The failure is by chance, so one green hosted run is weak evidence; the arithmetic and the planted faults carry the argument.
