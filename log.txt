          product the user has to manage.
[DECIDED] Bounded rollback of code and data migrations; reversible steps preferred
          over destructive in-place edits.
[DECIDED] Evolution is high importance; conversation stays usable; separate
          Evolution pane on the left, conversation on the right.
[REJECTED] Fixed daily "evolution budget"/quota. Use adaptive allocation instead,
          with runaway protection rather than a hard everyday allowance.
[REJECTED] Pure rewrite in Rust. Keep Python/Qt host + native inference; use Rust
          only for a measured bottleneck.
[DECIDED] UI: larger readable text, adjustable scaling, flexible saved panel
          widths, richer avatar. Original MARK identity retained.
[DECIDED] Humanistic decision principles + metacognition, but only user-approved
          ones are durable. No AGI claims.

--- Phase 3b — security/performance rethink (user asked for a critical pass) ---
[DECIDED] A staging directory is NOT a sandbox. Generated code must run with
          restricted filesystem, no production credentials, no personal memory DB,
          and constrained network.
[DECIDED] Activation approval must be bound to the exact patch hash + dependency
          set + test evidence + requested permissions. Any later edit invalidates
          the approval.
[DECIDED] A small separately-protected supervisor owns approval validation,
          activation, migration and rollback — enforced by real permissions, not
          prompt text. The evolving agent must not be able to edit it.
[DECIDED] Rollback cannot undo external effects (sent message, purchase). Mutating
          actions on real accounts stay out of unattended testing.
[DECIDED] Memory provenance is explicit: user-stated / user-approved inference /
          external claim / temporary hypothesis. Retrieved content and repo text are
          data, never instructions that grant permission.
[DECIDED] Adaptive compute, finite inspectable jobs: completion criteria,
          checkpointing, cancellation, and a stated reason to extend scope.
[DECIDED] Evolution and conversation coordinate shared provider quotas; separate
          keys do not imply separate limits.
[DECIDED] Cloud-first for heavyweight evolution on this laptop; local inference
          optional rather than a mandatory large download.
[DECIDED] Evaluate updates on outcome quality and responsiveness (audio
          interruption, GUI stalls, latency, memory growth), not test count alone.
[DECIDED] Data-sharing policy per provider: public/synthetic content may use free
          tiers; private code/personal context only with explicit permission; no
          silent provider fallback that changes privacy terms or adds cost.

2026-11-05  PHASE 4 — delegation, desktop automation, autonomy, providers
-------------------------------------------------------------------------------
[DECIDED] Sub-agents are a native MARK capability with explicit roles
          (researcher / planner / implementer / tester / reviewer), scoped context,
          no self-granted permissions, structured evidence, cancellable, visible in
          the Evolution pane. Delegation is selective, never per-command.
[DECIDED] Easy sub-agent roles (classification, diff summary, first-pass critique,
          tool-arg shaping) run on a LOCAL model to conserve API quota. Deterministic
          verification of anything a local model emits. Local model may never approve
          or activate.
[DECIDED] Background-first app control: "write these reminders" must populate the app
          without stealing the screen; app stays available in the taskbar.
           Hierarchy: app/document API -> UI Automation -> off-screen Win32 desktop
          session -> announced foreground handoff. Never type into an unverified
          window; never click stale coordinates; abort on target ambiguity.
[DECIDED] Specialised native helper tools ("desktop operator") are the approved shape
          for this, exposed to Python over local IPC behind capability tokens — not
          more pyautogui inside actions/. Some apps genuinely cannot be driven in the
          background; MARK must report that instead of faking success.
[DECIDED] Semantic app resolution: interpret "browser" as a capability, consult the
          registered default handler / installed-app metadata / already-running
          windows, verify the launched identity, reuse an existing session when
          sensible. No hardcoded browser name list. Ask one short question when truly
          ambiguous.
[DECIDED] Over-confirmation is a defect. Replace the 4-name READ_ONLY allowlist with
          risk-tiered consent: user-initiated reversible actions execute immediately
          (undo-tracked); destructive/irreversible/external actions confirm; camera
          and screen capture need explicit consent, visible indicator and stop control.
          Task-level session scopes avoid repeat prompts.
[DECIDED] The requested instruction itself can serve as consent for the requested act
          (e.g. "open the camera"); an unrelated task may not.
[DECIDED] Speed comes from direct execution + discovery caching + short task context +
          persistent connections + parallel independent reads, not from removing
          safeguards. Targets must be measured on the real machine.
[DECIDED] Multi-provider setup at first launch (optional credentials, not mandatory),
          Windows-protected secret storage (not plaintext config, not prompts),
          model discovery + capability validation, and voice switching of provider and
          model for conversation / evolution / critic separately.
[DECIDED] Fallback ladder ends at a local model, and a capability downgrade must be
          visible (queue or pause rather than silently emitting a weaker repair).
[SUPERSEDED] Earlier claim that MARK is Google-AI-Studio-only. Upstream already ships
          an OpenAI-compatible provider layer + engine UI (providers/, "ENGINE &
          PROVIDERS"). The real gaps are voice switching, per-purpose routing, quota
          grouping and secret storage.

            earlier hard rule (two approvals, nothing activates unattended).
            ASSISTANT POSITION: predictions may set ORDERING and DEFAULTS, never
            PERMISSIONS, and never for protected classes (policy, test roots,
            self-modification, credentials, money, messages, deletions).
            PROPOSED: calibrated predictor, threshold expressed as a lower
            confidence bound (>=0.70 of an 80% interval), active only for
            reversible non-protected actions, only after it proves calibration on
            held-out decisions, always with an undo receipt in the HUD. The
            predictor must be unable to vote on its own threshold.
            STATUS: awaiting user sign-off on that modification.

            test.

[DECIDED 8] UI accepted: draggable and saved pane widths, 100-200% text scale,

PART 2 — RECURSIVE SELF-IMPROVEMENT, THE HONEST VERSION
    The loop in core/selfimprove.py is real: propose candidate values for
    something Ultron owns (thresholds, ranking weights, prompt wording, tool
    order, retry budgets), score every candidate against the current value on the
    SAME held-out cases, and keep one only if it clears an exact paired sign test,
    a minimum effect size, a minimum case count, and breaks no safety case.

    What it deliberately is not: a model rewriting its own weights. That needs a
    training pipeline, a GPU, a licence to ship a different model, and would buy
    very little on a 1.5-3 B local model. Saying so is part of the deliverable.

    The arithmetic that makes it worth anything:
      - the sign test is exact and needs no distribution: 5 wins of 5 gives
        p = 0.0625 and is NOT accepted; 6 of 6 gives 0.0313 and is;
      - a mean can rise while the votes are 2-2, so the gate requires both;
      - any regression on a case marked safety rejects the candidate whatever the
        average says — a change that helps ninety tasks and breaks one file is not
        an improvement;
      - protected artefacts (code, permissions, the confirmation gate) return
        needs_human with the evidence attached, never an automatic accept;
      - every accepted change is journalled with the value it replaced, so one
        call reverts it.

THE AUDIT (run before changing anything)
    Imported every module added in PHASE 17 and 18: all fifteen import clean.

DEFECT 1 — acting on a ref never worked (the whole point, broken)
    actions/ui_control.py built a NEW Session on every tool call. A Session holds
    the snapshot id its refs belong to; a new one takes a new snapshot before
    acting, so the ref the model had just read was already from the previous
    snapshot. Measured: snapshot returned @523be7251d:e1, the next call answered
    "ref @523be7251d:e1 belongs to snapshot 523be7251d, not 063f8b3fda" and the
    adapter was never called. Every ref was decorative.
    Fix: one session per process, rebuilt only when the bridge changes, plus
    reset_session() for the case where it should be forgotten. Measured after:
    snapshot -> act by ref performs the invoke, and reusing the same ref after an
    action is refused with a stale-ref error, which is the intended behaviour.

DEFECT 2 — a batch could not run more than one step
    An action marks the snapshot stale on purpose, and the batch loop did not look
    again, so step two had nothing legitimate to resolve against. Measured: a
    three-step form fill (two fields, then Save) performed ZERO actions.
    Fix: the batch looks again before each step and refers to elements by name,
    because a ref belongs to one snapshot. A ref given for a later step now stops
    the batch with a message saying exactly that, rather than acting on whatever
    now sits at that number. Measured after: all three steps performed, three
    snapshots, in order.

DEFECT 3 — self-improvement had no engine
    core/selfimprove.py could decide whether a change was real. Nothing invoked
    it. A loop nothing can start is not self-improvement; "Ultron should be able
    to self-evolve" was therefore not yet true, and that was the most important
    finding of this phase.
    Fix: scripts/evolve.py. It measures a named artefact against cases, prints the
    verdict, and appends it to memory/evolution-log.json. It never edits source,
    by design: a program that rewrites itself while running is a program whose
    next failure nobody can reproduce, and the standing rule is two human
    confirmations for a change to code.
    Proved it both ways on the repo's own fixture: with the value in use (0.75) it
    reports "nothing tried was better by enough to be believed"; with a floor set
    too high (0.95) it proposes 0.65 with 6/18 cases better, 0 worse, p=0.0313,
    and still changes nothing.

SMALLER FIXES IN THE SAME PASS
    - a dead `waited` variable and a `del` after a return in the wait loop;
    - the renderer's "N more elements" count was computed from the budget rather
      than from what was printed;
    - an annotation referring to `Optional` after the import had been pruned
      (harmless at runtime because annotations are deferred, wrong on inspection);
    - the evolve log path was bound as a default argument, so it could not be
      pointed elsewhere without editing the file.

WHAT WAS ACTUALLY WRONG

    A. The interface scale existed and could not be reached. `ui_scale` was read
       from config at launch and applied through QT_SCALE_FACTOR, but nothing in
       the UI could set it: the only way to change it was to hand-edit
       config/api_keys.json. And the automatic value was too small — 1080/900 =
       1.20 on a 1080p laptop, a fifth larger and still, correctly, reported as
       small.

    B. First-run demanded Gemini. SetupOverlay had one field, GEMINI API KEY, and
       _check_config returned False without it — so an owner with a Groq key or a
       local Ollama could not start the app at all. The requirement is "any or
       several provider APIs, configurable at launch".

    C. Reopening setup erased everything else. _on_setup_done wrote a two-key
       file straight over api_keys.json. The app opens that screen by itself when
       a key is rejected, so an expired key silently reset the assistant's name,
       voice, colour, interface scale and every configured provider.

    D. The reconnect loop was a hot loop. The branch that handled "the resumption
       handle was rejected" fired whenever the exception text contained the
       substring "handle" — including "cannot schedule new futures after shutdown
       while handling audio" — and answered by setting the backoff to 0 and
       `continue`, which skips the sleep at the bottom of the loop. Connect, die,
       log, connect, die. That is the column of identical lines in the
       screenshot, and the reason the real error never reached the screen.

    E. The name was hardcoded in the two lines a user sees first:
       "SYS: JARVIS online." — while the window title, logo and greeting all said
       ULTRON.

    F. Found while rendering the fix: the first-run panel was placed at
       (-10, -90), because _show_setup computed its geometry before the window
       had laid out. On a 1920x1080 display the top and left of the very first
       screen sat outside the window.

    G. Found by the test for F: an added provider row was drawn twice, because
       takeAt() removes a widget from a layout without unparenting it and
       deleteLater() only queues the deletion — so the previous row stayed on
       screen until the next event-loop turn.

    ui.py
      CustomizeOverlay gains INTERFACE SCALE: 100 / 115 / 130 / 145 / 165 / 185 %

BUILD 1.2.6. Nine defects, every one found by driving it, every one with a test.

  1. A NULL ARGUMENT CRASHED SIX TOOLS. `dict.get(key, default)` returns the
     default only when the key is ABSENT, so a model that sends "action": null —
     which Gemini does for optional fields — got None and called .lower() on it.
     Six of the seventeen actions answered with "Tool 'file_controller' failed:
     'NoneType' object has no attribute 'lower'", which is not something a model
     can act on. Fixed at the dispatch boundary, so it covers all of them and
     every action written later; the eight inline tools in main.py get the same
     treatment where their arguments arrive.
  2. A WRONG-TYPED ARGUMENT CRASHED THEM TOO. "action": 5, "volume": "loud",
     "count": "7". The declaration already says which type each parameter is, so
     the value is now coerced to that type before any handler sees it. Anything
     that cannot be coerced is left alone and refused in words.
  3. CONCURRENT MEMORY WRITES LOST FACTS — silently. update_memory read the
     store, merged, wrote; load_memory and save_memory each locked their own
     half, which does not make the whole operation atomic. Measured: six threads,
     thirty writes each, 53 of 180 remembered facts survived. No error, no

PHASE 26b — THE CAPABILITY THAT WAS LYING ABOUT ITSELF. 2026-11-06
-------------------------------------------------------------------------------
Asked what else was gatekeeping the build, the honest way to answer was to audit
the dependencies rather than the prose. That audit found the worst defect of the
whole run, in the one place the design cannot afford one.

BUILD 1.2.8. The accessibility tree reported itself available and could not walk
a single node.

  "Accessibility tree before vision" is a standing requirement, and it rests on
  core/ui_windows.py. Its available() checked uiautomation, and failing that,
  pywinauto — answering "usable, pywinauto". But pywinauto is installed on every
  Windows machine this app sets up, because three plugins import it directly, and
  the pywinauto branch of the driver raises NotImplemented. So on a fresh install
  the ladder would prefer the tree over vision exactly as instructed, and the
  first real action would fail with a message about a package the user had never
  heard of. The capability looked present, was selected, and threw.

  Three things were wrong and all three are fixed:
    1. uiautomation — the package the driver is actually written against — was
       not a declared dependency at all. Now it is, in requirements.txt, and
       core/installer.py knows its name so the in-app installer can add it.
    2. available() confused "a package is importable" with "a driver exists".
       It now answers usable only for a backend that can be driven, and when
       pywinauto is present on its own it says "pywinauto is installed but this
       bridge has no pywinauto driver; install uiautomation". A capability that
       reports itself ready and then throws is worse than one that reports
       itself missing.
    3. scripts/verify_windows.py imported uiautomation itself to test the tree,
       so its instrument could report SKIP while the product believed the tree
       was fine. It now asks core.ui_windows.available() — the same question the
       product asks. An instrument that answers a different question measures
       nothing.

  tests/test_ui_bridge.py (9 tests) holds the invariant: usable is true only when
  a driver exists AND its package is installed; if available() ever reports a
  backend with no driver, _module() must fail loudly rather than silently; and
  the declared dependency cannot be dropped without a test going red.

NOT VERIFIED, UNCHANGED
  The bridge has still never walked a real Windows tree. That is a proof gap, not
  a defect, and scripts/verify_windows.py is the instrument that closes it. If it

BUILD 1.2.9. scripts/proof_gate.py: sixteen claims, four verdicts.

  A component check says "the microphone records". A claim is a chain: sound
  arrives, the words are recognised, the model answers, the answer comes out of
  the speaker. Those are different questions, and only the second one is the
  product. Each claim prints every step, so a chain that breaks at step three
  says where.

  PROVEN        every step ran and fed the next
  PARTIAL       some steps proved, a later one needed hardware, an OS or a key
  FAILED        a step ran and produced the wrong thing
  NOT PRESENT   there is no code behind the claim at all

  NOT PRESENT is the verdict that matters, because it is the one an enthusiastic
  report rounds up to "works". Two claims reach it here, and they are the real
  finding of this build.

  MEMORY IS NOT APPROVAL-ONLY. save_memory writes immediately and returns
  silent: true. The model can persist an inferred preference without asking. The
  standing rule is "only remember what the user approves"; the code does not
  implement it. Not a bug in the sense of a broken function — a missing one.

  THE DAILY DIGEST DOES NOT EXIST IN ULTRON. The only "digest" in the tree is an
  md5 hash in background_monitor.py. It is an Agentic OS milestone property.
  Claiming it here would have been inventing a feature, so the gate says NOT
  PRESENT in those words.

BUILD 1.2.10. core/memory_consent.py, and one call site changed.

  The rule was already written down. core/policy.py has classified save_memory as
  GUARDED since the policy table existed: "memory is permanent — remembering is
  approval-gated". The verdict was there. The inline tool path in main.py never

  tells it to ask out loud and forbids claiming it is done, and the banner shows
  the fact verbatim — the user approves the value, not a summary of it.

WHY THERE IS NO "THE USER ALREADY SAID REMEMBER" SHORTCUT
  It would be the obvious optimisation and it is the wrong one. Deciding that
  intent from an utterance means "do you remember what I told you?" saving
  silently when the classifier guesses wrong, and being wrong in that direction
  writes something permanent without asking. One confirmation for a permanent
  change is not the trivial-action prompting to be avoided.

TWO QUALITY DETAILS THAT MATTER MORE THAN THE FEATURE
  1. ONE BANNER AT A TIME. The gate holds a single pending decision. A second
     memory write would have replaced the first and the fact behind it would have
     vanished with no error anywhere — the exact silent loss this module exists
     to stop. It now answers "I already have a confirmation on screen" and the
     first decision stays intact.
  2. A GATE THAT CANNOT ASK SAVES NOTHING. If no interface is bound (headless,
     early startup), confirm.request already refuses; that sentence now reaches
     the model unchanged instead of becoming an implied success.

  The write path is also single: policy-allow (nothing in this build) and
  policy-guarded both funnel through one function, so there is one place to audit.

THE DIGEST IS NOT AN ULTRON CLAIM AND WAS REMOVED FROM THE GATE
  It was reported NOT PRESENT because there is no daily digest in Ultron. True,
  and beside the point: the digest is an Agentic OS milestone property. Keeping
  it in this gate meant the instrument punished Ultron for not having a feature
  nobody asked Ultron for. Removed rather than built — a digest is new feature
  work and this app is frozen.

BUILD 1.2.11.

THE DIGEST — core/digest.py, and it activates nothing by construction
  The standing rule is one sentence: the digest activates nothing. So the module
  is shaped so that it cannot: build() reads three local files and returns a
  plain dict, render_*() turn that dict into words, should_run() decides whether
  today is due — and none of the three opens a socket, starts a process, calls a
  tool or writes a file. The single write in the whole module is save_last_run(),
  which stores one date so the digest runs once a day.

  What it reports: facts remembered today (from the memory store, by the date
  each entry carries), how many older facts exist, the topics being watched, and
  how many reminders are set by name. Nothing else. News checking stays in
  background_monitor; reminders stay in reminder.py. A digest that quietly did
  their work would be the worst kind of feature: one the user believes is inert.

  Three details that are decisions, not accidents:
    1. It does not import actions/reminder.py — that module's helper CREATES its
       folder, and a digest that creates a folder is a digest that changed the
       machine. The path is built locally instead, and a test asserts that a
       missing folder stays missing.
    2. Watched topics are machine state, not things the user asked to remember,
       so they are reported in their own line and excluded from the fact count.
    3. The spoken version is capped at 240 characters. The digest must not hold
       the floor while the user is talking.

  Delivery, twice: the `daily_digest` tool for when the user asks, and a daily
  loop that writes the report to the activity log at the configured hour (default
  20:00, memory/config_manager.get_digest_hour). The loop never speaks — a
  summary that interrupts is not a summary. It checks every ten minutes; the
  check is a string comparison.

  Tests: tests/test_digest.py (22). The ones that matter are the inert ones —
  building with socket.socket and subprocess.run replaced by functions that raise,
  and a before/after snapshot of the memory folder proving nothing was touched.

THE FAILED TEST WAS THE INSTRUMENT'S FAULT
  sees_screen reported FAILED because screen capture raised "Cannot connect to
  display" — on a container with no screen. The feature did not fail; the
  question did not apply. That is the definition of SKIP, and the gate has had
  SKIP since the day it was written. It now asks one more thing before judging:
  is there a display at all (DISPLAY/WAYLAND_DISPLAY on Linux, always on Windows
  and macOS)? No display becomes SKIP with the reason; a display that returns no
  frame stays FAILED, because that is a real fault.

  This is the distinction the whole gate exists for. A report that says FAILED on
  a machine that could not answer teaches the user to ignore the colour.

BUILD 1.2.17.
  Ultron can ship its own work, and update itself from GitHub. Session state survives.
  1. custom_jarvis/ship.py — Shipper: scan, guards, syntax, optional gate, commit, push.
     The order is the design: a secret is caught before the commit exists, and a
     broken file is caught before it is published. The note names the stage that
     refused, so "it did not ship" is never a mystery.
  2. The scanner separates a key from a fixture. A github_pat_ string must be over
     60 characters; an assignment-shaped value must not read as test, example,
     dummy, sample, probe, placeholder, xxxx, abcd, 1234, your, todo or changeme.
     Without that rule the scan reported three false alarms on this repository's
     own test fixtures, and a scanner that cries wolf gets ignored.
  3. Push is fast-forward only. A diverged remote is a refusal sentence with the
     word "will not force" in it, because the alternative is destroying published
     work. Every attempt is kept in ship_log.json, last 100.
  4. custom_jarvis/selfupdate.py — Updater: check, apply, restart_marker. Refuses a
     dirty tree, pulls --ff-only, verifies that every .py parses, and resets to the
     previous commit when one does not. A .py change writes a restart marker naming
     the files; a data change does not, because packs, config and workspace data
     are read from disk on demand.
  5. custom_jarvis/ship_tools.py — ship_status, ship_now, check_update,
     apply_update. The two readers are in the read-only set; the two actors are
     not, so publishing and pulling each ask the owner first.
  6. config/api_keys.json may carry ship_auto. Off unless the owner writes it,
     because a push is public and this machine cannot un-publish it. With it on,
     add_skill and remove_skill ship themselves in one background thread with the
     change as the reason; with it off the change waits in ship_pending.json and
     ship_status reports it as waiting.
  7. Two new proof-gate claims, both against a real bare git remote in a temporary
     folder, with no mocks: shipping (seven steps) and self_update (six steps).

  byte-identical, 1,642 lines each. GitHub runs `run:` steps in PowerShell, and

  failed step. This suite writes tracebacks to stderr on purpose, because several
  tests check that an error comes back as a sentence. The Windows steps now run
  under bash, and `tee` keeps each console in the artifact, so the next red job
  arrives with its own evidence.
